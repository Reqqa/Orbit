# Orbit

**Orbit, payment reconciliation for the Orbyte hub.**

S.D.C. Hackathon 2026 — Domain 2, Orbyte Smart SME Challenge.
Orbit is a module for the **Orbyte** business hub. Orbyte is the host platform; it is not us.

---

## The problem

Malaysian micro and small businesses run on WhatsApp. Customers pay by DuitNow, bank
transfer or e-wallet and then send a screenshot of the receipt. The owner opens each
chat at night, squints at the screenshot, checks the bank app, ticks a spreadsheet, and
chases late payers by hand.

## The approach

Orbit turns that WhatsApp thread into a controlled workflow:

1. **Trigger** — a customer sends a payment receipt to the business's WhatsApp number.
2. **Connected data** — open invoices, customer and role data come from the Orbyte hub
   through a connector.
3. **Decision logic** — AI reads the image; **deterministic rules** score the match on a
   100-point scorecard and classify it as one of eight cases.
4. **Human approval** — the right role approves with one tap. Role and amount limit are
   enforced on the server, and every refusal is logged.
5. **Visible outcome** — the payment is recorded, the invoice moves to PARTIAL or PAID,
   the customer gets a templated confirmation, and the dashboard and the tamper-evident
   audit log update.

Overdue invoices are then chased on a fixed ladder with pre-approved message templates,
sent only after the owner approves the batch.

**Orbit never moves money.** It records and reconciles payments that already happened.
No refunds, no statutory filings, no financial advice.

---

## The expected outcome

**Measured on the 50-receipt test set** (reproduce with `scripts/eval_accuracy.py`):

- **47 / 50 (94%)** of receipts classified correctly by the deterministic decision path.
- **0** confident wrong answers — no receipt scored 90+ against the wrong invoice.
- **100%** of recorded payments human-approved, role-checked and written to a
  tamper-evident log. Nothing is ever recorded without a person pressing Approve.

**Assumptions, not measurements** — stated as targets, to be validated with real owners:

- Per-receipt handling falls from roughly 3 minutes to about 20 seconds.
- Owner reconciliation time falls from roughly 6 hours a week to about 1.

**SDG contribution.** Primarily **SDG 8** — target **8.2**, productivity through
technological upgrading, by removing a nightly manual task; and target **8.3**, support
for the growth of micro and small enterprises, since late payments and reconciliation
errors are a cash-flow problem before they are an admin problem. Secondarily **SDG 9**,
as a reusable module on shared digital infrastructure rather than a bespoke system each
SME pays to build.

## Setup

You need **Python 3.12+** and **Node 20+**.

### Windows (PowerShell)

```powershell
git clone <your-repo-url> Orbit
cd Orbit

# 1. Python backend
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r backend\requirements.txt

# 2. Secrets. Copy the template, then generate two real keys.
Copy-Item .env.example .env
python -c "import secrets; print('SESSION_SECRET=' + secrets.token_urlsafe(32))"
python -c "import secrets; print('PHONE_HMAC_KEY=' + secrets.token_urlsafe(32))"
# Paste both into .env, replacing the change-me placeholders.

# 3. Demo data: 3 tenants, 75 customers, 80 invoices, 50 labelled receipts
cd backend
python -m seed.generate_data --reset
python -m seed.generate_receipts
cd ..

# 4. Dashboard
cd frontend
npm install
Copy-Item .env.local.example .env.local
cd ..
```

### macOS / Linux

```bash
git clone <your-repo-url> Orbit && cd Orbit

python3.12 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements.txt

cp .env.example .env
python -c "import secrets; print('SESSION_SECRET=' + secrets.token_urlsafe(32))"
python -c "import secrets; print('PHONE_HMAC_KEY=' + secrets.token_urlsafe(32))"
# paste both into .env

cd backend && python -m seed.generate_data --reset && python -m seed.generate_receipts && cd ..
cd frontend && npm install && cp .env.local.example .env.local && cd ..
```

`PHONE_ENC_KEY` can stay empty: the encryption key is then derived from
`PHONE_HMAC_KEY` so a fresh checkout runs without extra setup. For anything beyond a
demo, generate a real one:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

## Running it

### One URL (what judges see, and what you demo)

Build the dashboard once; FastAPI then serves it alongside the API on a single port.

```bash
cd frontend && npm run build && cd ../backend
uvicorn app.main:app --port 8000
```

Open **http://127.0.0.1:8000** for the dashboard and
**http://127.0.0.1:8000/docs** for the OpenAPI page.

### Two terminals (while developing)

```bash
# terminal 1
cd backend && uvicorn app.main:app --reload       # API on :8000

# terminal 2
cd frontend && npm run dev                        # dashboard on :3000
```

In development Next.js proxies `/api`, `/v1` and `/webhooks` to the Python backend, so
the browser still sees a single origin. Open **http://localhost:3000**.

### The 60-second demo path

1. **WhatsApp simulator** — as the Owner, pick **Chee Hwa Peng Mini Market**, attach
   `backend/seed/receipts/001-exact-match.png`, press Send. Each receipt is labelled for
   one customer, so match the two: this one pays INV-1003, RM 677.45.
2. **Approvals** — the receipt is there with the image, the extracted fields, the
   suggested invoice, a confidence bar and a plain-language "why we think so".
3. Switch the role dropdown to **Ravi Chandran · SALES** and press Approve. You get a
   refusal, and the attempt is written to the audit log. Sales only sees the customers
   assigned to them, which is why step 1 uses one of Ravi's: a receipt from
   `010-exact-match.png`'s customer would not be on his screen at all.
4. Switch back to **Lim Wei Keong · OWNER**, press Approve. INV-1003 moves to PAID, and
   the customer's thread in the simulator now shows the templated confirmation. Nothing
   is sent to the customer before a person approves.
5. **Ledger** — click the invoice to see its timeline.
6. **Audit log** — press *Verify integrity*. Then tamper with a row and press it again:

   ```bash
   sqlite3 backend/orbit.db "UPDATE audit_log SET after_json='{\"tampered\":true}' WHERE id=5;"
   ```

   Verification now fails and names row 5.
7. **Chasing** — press *Run now* to draft today's reminder batch, with every skipped
   customer and the reason it was skipped.

Try the different receipt types: `*-partial-payment`, `*-overpayment`, `*-duplicate`,
`*-two-invoice`, `*-blurry`, `*-not-a-receipt`.

```bash
cd backend && python -m pytest -q
```

Deliberately narrow (`docs/SPEC.md` §14.3) — the four places where a silent bug would be
expensive:

| File | What it proves |
|---|---|
| `tests/test_matching.py` | The scorecard: exact, partial, overpayment, reference normalisation, alias matching, phone match, future dates, ranking and tie-breaks, multi-invoice sums |
| `tests/test_classify.py` | All eight classifications and their precedence |
| `tests/test_rbac.py` | Sales cannot approve, Finance cannot exceed its limit, every refusal is audited |
| `tests/test_audit_chain.py` | Editing or deleting any audit row breaks verification, and tenants' chains are independent |

There are no tests for the UI, the webhook or the seed scripts, on purpose.

## Accuracy

Measured over the 50 labelled synthetic receipts, on a freshly seeded database:

| Measure | Result |
|---|---|
| Classification accuracy, against the real decision path | **47 / 50 (94.0%)** |
| Top candidate scored ≥ 90 **and** was the labelled invoice | 22 / 50 (44.0%), or 22 / 45 (48.9%) of the receipts that have a labelled invoice at all |
| Top candidate scored ≥ 90 but was the **wrong** invoice | **0** |
| Routed to a human instead (no candidate reached 90) | 28 / 50 (56.0%) |
| Extraction, per field, with the `mock` extractor | 100% *by construction — see below* |

Reproduce it with:

```bash
cd backend && python -m seed.generate_data --reset && python ../scripts/eval_accuracy.py
```

Full report with the confusion matrix: [`docs/accuracy.md`](docs/accuracy.md).

Three things worth saying plainly:

- **The extraction figures are not a measurement of the model.** With the default `mock`
  extractor they are 100% by construction, because the mock reads the same label file
  the eval compares against. They measure the plumbing. Run
  `python ../scripts/eval_accuracy.py --provider claude` with an API key to measure the
  model. The matching and classification figures are real either way: that code never
  sees the labels.
- **The auto-match rate is the test set, not a weakness.** Only 15 of the 50
  receipts are clean exact matches; the rest are deliberately awkward — partial
  payments, overpayments, two-invoice payments, duplicates, cropped references, blurry
  images, wrong amounts, a non-receipt photo. Everything that does not clear 90 goes to
  a human on purpose, and **no receipt scored ≥ 90 against the wrong invoice**. A
  confident wrong answer is the expensive failure in a payments product, so it is
  counted on its own line.
- **All three misses are the `DUPLICATE` rows, and they are an artefact of the eval.**
  Duplicate detection needs the earlier copy to already be in the ledger, and the eval
  approves nothing, so it sees each receipt in isolation. Duplicate detection is
  verified working end to end in both of its forms — against a recorded payment
  ("already recorded") and against an earlier copy still waiting for a decision — and
  you can watch it in the demo with `032-duplicate.png` after sending
  `010-exact-match.png`.

## Orbyte fit

Orbit is an Orbyte **app module**, not a standalone app. Hub data crosses one boundary,
`OrbyteConnector`. Two of its reads and both of its writes are on the live path today:
every match decision is scored against invoices and customers fetched through it, and
every approval writes a payment and an activity event back through it. The tenant and
user reads behind the simulated login still read locally, because login and RBAC are
the platform foundations the brief says may be simulated.

| Direction | What crosses | Assumed endpoint |
|---|---|---|
| Read | company profile and timezone | `GET /orbyte/v1/tenants/{id}` |
| Read | users and roles, the RBAC source of truth | `GET /orbyte/v1/users?tenant={id}` |
| Read | customer master data and aliases | `GET /orbyte/v1/customers?tenant={id}` |
| Read | the invoices every receipt is scored against | `GET /orbyte/v1/invoices?status=open` |
| Write | an approved payment, with an idempotency key | `POST /orbyte/v1/payments` |
| Write | Orbit's audit events, into the hub's shared log | `POST /orbyte/v1/activity-log` |
| Write | optional in-hub alerts | `POST /orbyte/v1/notifications` |

We define that interface ourselves, as the brief allows — there was no live Orbyte
access. The MVP ships `MockOrbyteConnector`, which reads the synthetic demo data and
echoes the writes. A real connector implements the same interface and **nothing else in
Orbit changes**.

This is not a claim you have to take on trust: `GET /api/orbyte/status` reports which
connector is answering, what it can currently see, and what gets written back;
`GET /api/orbyte/preview` shows the raw records, `"simulated": true` and all. Every
approval leaves a `HUB_SYNCED` row in the audit log recording whether the hub accepted
the payment and the activity event.

**What deliberately never crosses to the hub:** the keyed phone HMAC Orbit uses to
recognise a sender, the receipt images, the extractions, the match proposals and the
hash-chained audit log. Those are Orbit's own.

**Reuse:** the demo database holds three tenants — a hardware trader, a bakery supplier
and a tuition centre. The role switcher moves between them, and it is the same code and
the same rules each time, differing only by tenant configuration.

## How it works

```
WhatsApp (or the built-in simulator)
        |  Meta-shaped webhook payload
        v
FastAPI  ->  store message (duplicate wa_message_id ignored)
        ->  EXTRACTION (the only AI)  mock | claude-opus-5-5 vision
        ->  MATCHING (pure functions, 100-point scorecard)
        ->  CLASSIFICATION (8 cases, templated explanation)
        ->  PROPOSAL routed to Finance or Owner by amount and confidence
        v
   Approval inbox  ->  human decision  ->  one transaction:
                                           payment + allocations + invoice status
                                           + audit rows, then a templated reply
        v
SQLite  (11 tables, every row tenant-scoped, audit log hash-chained)
        ^
Next.js dashboard (static export, served by FastAPI)
```

The match scorecard (`docs/SPEC.md` §7.2), weights configurable per tenant:

| Signal | Weight |
|---|---|
| Amount equals the outstanding balance | 40 |
| Reference contains the invoice number | 25 |
| Payer name similar to the customer or an alias | 15 |
| Sender's phone matches the customer on file | 10 |
| Date is plausible | 5 |
| It is the customer's only open invoice | 5 |

≥ 90 is a strong match, 70–89 is "likely, please check", below 70 goes to a human.
Anything that is not a clean exact match is an exception and always goes to the Owner.

### Design rules the code actually follows

- **AI only where it adds value.** A model reads images. Nothing else. Matching,
  classification, approval limits and the chase ladder are deterministic Python.
- **Nothing consequential without a human.** Recording a payment and sending a reminder
  batch are both gated by role and amount limit.
- **Explainable by default.** Every recommendation cites the signals that matched and
  names the ones that are missing, in templated text, never model prose.
- **Money is integer sen.** RM 850.00 is `85000`. No floats anywhere.
- **Multi-tenant from the first table.** Three tenants in the demo data.
- **Append-only, hash-chained audit log.** Each row stores the previous row's hash and
  is written in the same transaction as the change it records.

## Privacy and PDPA

- Phone numbers are stored twice: a **keyed HMAC** for lookup and an **encrypted** copy
  used only to send replies. A plain hash of a Malaysian mobile number is brute-forceable,
  so the lookup value is keyed.
- The dashboard only ever displays the last four digits.
- Receipt images are stored as a reference, never as bytes in the database.
- The audit log records who did what, when, and whether it was a human, the system or
  the AI.
- Webhook payload signatures are verified when an app secret is configured.
- A real deployment would add: customer consent and a STOP keyword, retention and
  deletion of receipt images after a configurable period, signed URLs for media, and
  disclosure of the LLM provider with a self-hosted option for sensitive tenants.
- This MVP uses synthetic data only.

Full table: `docs/SPEC.md` §10.

## Risks

The hardest risk is **WhatsApp Business API access** — Meta business verification,
number registration and template approval all take time we do not control. The fallback
is built and is what you see in the demo: a channel simulator using identical webhook
payloads, so the pipeline being demonstrated is the pipeline that ships. Everything
simulated is labelled as such in the UI, in the API responses and in this README.

The live Cloud API path is now written but unverified, and the three chase reminders
would need approved template messages before they could go out for real: see
[`docs/connect-whatsapp.md`](docs/connect-whatsapp.md) and the §12 risk table.

Other risks and their fallbacks: `docs/SPEC.md` §12.
